Return Risk Intelligence: Predicting Return Probability, Return Fraud & Product Quality Issues

A PySpark/MLlib solution that separates genuine returns, product-quality failures, and fraud/abuse at the point of return request — so a retailer's return-audit team can act on the 1-in-3 returns worth a second look, instead of reviewing all of them.

Consulting Report · E-commerce Domain
Dataset: ecommerce_return_abuse_dataset.csv (Kaggle) — 60,000 orders × 35 features

Executive Summary

Retailers processing high return volumes cannot scale spreadsheet-based manual audits. This project builds an end-to-end Big Data Analytics pipeline — architecture, feature engineering, and two independent PySpark MLlib models — that triages every return request into legitimate, policy abuse, fraudulent return, or wardrobing, and separately segments customers/returns by behavior to surface product-quality problems the fraud label alone can't see.

Three findings drive the recommendations:

  1. Fraud is classifiable with high confidence from behavioral and evidence signals (tracking validity, photo evidence, address changes, refund-to-different-account) combined into an engineered fraud_signal_score — a Random Forest model built on these features reaches nearly perfect separation on this dataset (see the model-evaluation caveat in Section 6 before reading that number as a production guarantee).
  2. Return fraud and product quality are largely separate problems that get conflated in a single "return rate" metric. Clustering on behavior alone (no fraud label) finds a 73%-of-customers "core legitimate" segment whose returns are still 38% quality-issue driven — this is a QA/vendor problem, not a fraud problem, and needs a different owner and fix.
  3. A production system needs three different interventions, not one: automated fraud-score routing for the classifier's high-risk tail, policy tightening for the frequent-low-value-returner cluster, and category-level quality escalation for the segment carrying the highest quality-issue rate.

1 · Business Context & Problem Framing

An e-commerce retailer's return-audit team currently reviews disputed or high-value returns manually. That does not scale: return volume grows faster than headcount, audit criteria are applied inconsistently across reviewers, and the team has no systematic way to tell whether a spike in returns for a product category is fraud, abuse of a lenient return policy, or a genuine quality defect that needs a vendor escalation — three problems that call for three different responses, currently indistinguishable in a spreadsheet.

We map this one dataset onto three sub-problems:

Sub-problemApproachOwner in the business
Return fraudMulti-class classification on abuse_typeFraud & Risk team
Product quality issuesFilter return_reason ∈ {Defective/Broken, Quality Issue, Not As Described}, cross-cut by cluster and categoryQA / Vendor Management
Return probability / riskDerived from return_rate_pct, lifetime order/return history, per customerCustomer Ops / Policy

Why this matters financially

Of 60,000 orders in the dataset, 17,940 (29.9%) are non-legitimate returns (Policy Abuser 12.0%, Fraudulent Return 10.2%, Wardrobing 7.7%). Every one of those returns today gets the same manual-review treatment as a genuine defective-product return — the highest-value lever is triage, not blanket policy tightening, which would punish the 70% of legitimate customers too.

4 · Data Engineering (Phase 2)

Implemented in notebooks/01_data_engineering.ipynb, executed end-to-end against the full 60,000-row dataset with PySpark (not pandas/scikit-learn, per the course's distributed-computing requirement).

4.1 Data quality

Verified programmatically, not assumed: 0 nulls across all 35 columns, 0 duplicate order_id, 0 logical violations (no return-before-order dates, no returns-exceeding-orders, no implausible ages).

4.2 Outlier treatment

IQR-flagged outliers on 8 continuous fields were capped at the 1st/99th percentile rather than deleted. For a fraud dataset, extreme values are frequently the signal itself (an unusually large refund request, an unusually fast wishlist-to-cart flip); deletion would remove exactly the rows the model most needs.

4.3 Feature engineering

FeatureServesRationale
fraud_signal_scoreFraudAdditive count of 6 red-flags (address change, refund-to-different-account, multiple accounts, invalid tracking, no photo evidence, tampered packaging) — a single interpretable risk score
return_to_order_ratioReturn riskIndependently recomputed cross-check of the provided return_rate_pct
refund_to_order_value_ratioFraudRefund requested relative to order value — abuse/fraud skews this ratio
is_quality_issue_reasonQualityFlags Defective/Broken, Quality Issue, Not As Described — the slice QA owns vs. fraud
high_value_no_evidenceFraudInteraction flag for a known abuse pattern: high-value item + no photo evidence
Validation, not assumption: mean fraud_signal_score is 2.73 for Fraudulent Return vs. 0.84 for Legitimate, and mean return_to_order_ratio is 0.47 vs. 0.05 — confirmed in the notebook before these features were trusted for modeling.

4.4 Encoding & scaling

Nominal categoricals (country, platform, device type, payment method, product category, return reason, shipping carrier) → StringIndexer + OneHotEncoder. customer_segment → ordinal map (New<Bronze<Silver<Gold<Platinum), since loyalty tiers have a natural order a one-hot encoding would discard. Continuous features → StandardScaler — required for the distance-based K-Means model (Section 6.3); tree models don't need it but reuse the same pipeline for consistency. 75/25 train/test split, seed=42: 45,112 train / 14,888 test rows.

5 · Machine Learning (Phase 3)

Two independent PySpark MLlib approaches, implemented in notebooks/02_ml_modeling.ipynb, satisfying the ≥2-approach requirement.

5.1 Approach 1 — Multi-class classification (return fraud)

Random Forest (200 trees, maxDepth=10, class-weighted) vs. multinomial Logistic Regression baseline, on abuse_label. Spark MLlib's GBTClassifier only supports binary classification — not usable for this 4-class target — so Random Forest, which natively supports multi-class, is the primary model.

Class imbalance (70/12/10/8) was handled via inverse-frequency weightCol training weights, not resampling — evaluation reports per-class precision/recall/F1, not headline accuracy alone, since a "predict Legitimate always" model would score ~70% accuracy while catching zero fraud.

Top feature importances (Random Forest)

Model-evaluation caveat (see also docs/fraud-classification-results.md): weighted F1 of 0.998–0.999 is unrealistically high for a live fraud operation. Feature importance is spread across ~15 features with no single dominant leak — this isn't a one-column shortcut — but this is a Kaggle synthetic dataset, and synthetic label generators typically compose the target from a fairly clean rule, producing near-separable classes real transactional data never gives you. We present this as proof of the pipeline and methodology: the architecture, feature engineering, and evaluation approach transfer to production; this specific accuracy number does not. A realistic production target is 80–90% weighted F1, and we recommend budgeting for that expectation, not this one, in any business case.

5.2 Approach 2 — K-Means clustering (quality & customer segmentation)

An independent, unsupervised lens: features deliberately exclude the fraud-flag columns used by the classifier, so clustering surfaces behavior/quality patterns a supervised fraud label can't. k=3 selected by silhouette score over k=2..6.

6 · Business Insights & Strategic Recommendations

  1. Deploy the fraud classifier as a triage score, not an auto-block. Route the highest fraud_signal_score decile plus Cluster 0 members to manual fraud review; auto-approve the lowest-risk tail. Re-validate precision/recall on live traffic before trusting this dataset's 0.999 F1 — budget for 80–90% in the initial production SLA.
  2. Give Cluster 1 (core legitimate, 73% of customers) to QA, not fraud. Its 38% quality-issue-return rate is the highest of the three segments despite near-zero fraud — cross-reference dominant product_category within this cluster against return_reason to identify which vendors/categories need a quality escalation.
  3. Tighten policy, don't investigate, for Cluster 2. High order/return volume, low order value, Policy-Abuser-dominated — a shorter return window or restocking fee targets this segment more precisely than a fraud investigation would.
  4. Re-threshold before deployment. A false "Legitimate → Fraudulent Return" flag costs more in customer trust than a slow manual review costs in ops time — set the classification threshold asymmetrically, not at a default 0.5, once real cost estimates are available.
  5. Re-validate quarterly. Fraud patterns adapt to whatever the model learns; without a temporal holdout in this dataset, we cannot measure drift here — production deployment needs a rolling time-based validation window from day one.

Risks & future roadmap

  • Risk — synthetic-data overfit to production: mitigated by treating this model as a pipeline proof-of-concept and re-training on real labeled fraud outcomes before go-live.
  • Risk — no ground-truth fraud labels in production: real retailers rarely have a clean abuse_type column; roadmap includes a human-in-the-loop labeling process from the manual review queue this system creates.
  • Future: real-time scoring at return-request time (not batch), a feedback loop from review-team overrides back into re-training, and extending clustering features with unstructured support-ticket text once the Flume/API ingestion (Section 3) is live.
