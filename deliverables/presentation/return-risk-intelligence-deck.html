The Problem

Manual return audits don't scale — and they treat three different problems as one

Retailers process every disputed return the same way: spreadsheet review, inconsistent criteria, growing backlog. Meanwhile 29.9% of returns in our dataset are not genuine — and each needs a different response.

  • Return fraud — deceptive claims → needs a Fraud & Risk response
  • Policy abuse — exploiting lenient terms → needs a Policy response
  • Product quality — genuine defects → needs a QA/Vendor response

Approach 1 — Classification

Random Forest vs. Logistic Regression on return-fraud type

ModelWeighted PrecisionWeighted RecallWeighted F1
Logistic Regression (baseline)0.9980.9980.998
Random Forest (final)0.9990.9990.999

Class-weighted training (inverse frequency) handles the 70/12/10/8 imbalance. GBTClassifier isn't usable — Spark MLlib supports binary GBT only; Random Forest natively handles 4 classes.

Honest read: 0.999 F1 is unrealistically high — this is a Kaggle synthetic dataset with a near-deterministic labeling rule. We treat this as proof of pipeline & methodology; a realistic production target is 80–90% weighted F1.

Recommendations

Three interventions, three owners — not one blanket policy

Ship this first, no ML required: require photo evidence above a value threshold — the "high-value + no evidence" pattern alone touches $1.88M of non-legitimate refund exposure (4,673 orders) and can go live before the classifier does.

Fraud & Risk

Route the highest fraud-score decile + Cluster 0 to manual review. Deploy as a triage score, not auto-block. Re-threshold asymmetrically — a false flag costs more than a slow review.

QA / Vendor Mgmt

Own Cluster 1's 38% quality-issue rate. Cross-reference dominant product category × return reason to target vendor escalations.

Customer Policy

Tighten return windows / restocking fees for Cluster 2's frequent-low-value pattern — more precise than a fraud investigation.

Before go-live: re-validate on real labeled outcomes (not this synthetic set), add a time-based holdout to catch drift, and build the human-in-the-loop labeling loop from the review queue.

Risks & Future Roadmap

What has to be true before this goes to production

Risks

  • Synthetic-data metrics won't hold on live traffic — treat as a pipeline proof-of-concept, not a performance guarantee
  • Real retailers rarely have clean fraud labels — needs a labeling process
  • No temporal holdout here — drift is unmeasured, must be built into the rollout

Roadmap

  • Real-time scoring at return-request time, not batch
  • Feedback loop from reviewer overrides back into re-training
  • Add unstructured support-ticket text once Flume/API ingestion is live
