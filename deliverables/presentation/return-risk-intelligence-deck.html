The business problem

One review queue, three different problems wearing the same form.

A return-audit team currently reviews every disputed return the same way. It has no systematic way to tell whether a spike in returns is fraud, abuse of a lenient policy, or a genuine quality defect — three problems that need three different owners, currently indistinguishable in a spreadsheet.

The question this project answers

Which returns are fraud, which are policy abuse, and which are genuine quality failures — and what does each one actually cost?

Three sub-problems, one dataset: return fraud → classification on abuse_type; product quality → return-reason patterns cut by cluster and category; return risk → lifetime order/return history per customer.

Why this is a triage problem, not a policy problem

The highest-value lever is routing each return to the right team fast — not tightening policy across the board, which would punish the 70% of customers who did nothing wrong. Three different interventions, three different owners, is the recommendation this whole pipeline builds toward.

Solution architecture · one picture

Sqoop / Flume / API ingestion → Bronze/Silver/Gold lakehouse → PySpark MLlib.

This notebook runs directly on the static Kaggle CSV as a practical stand-in — the diagram below is the production-scale design the Silver→Gold transformation logic is built to generalize to.

Why Bronze/Silver/Gold

Bronze keeps a permanent, replayable raw record. Silver is cleaned and feature-engineered once, reused by both models. Gold is the only layer anything ML touches.

Explicit schema, not inferred

The notebook loads the CSV with an explicit StructType — never inferSchema in production, which forces a full extra scan and can silently mis-type columns on drift.

Cap outliers, don't delete

Extreme values are often the fraud signal itself. 8 continuous fields IQR-capped at the 1st/99th percentile — preserving row count and the extremeness of the behavior.

Approach 1 — Classification

Random Forest vs. Logistic Regression on return-fraud type.

Spark MLlib's GBTClassifier only supports binary classification — not usable for this 4-class target — so Random Forest, which natively supports multi-class, is the primary model. Class-weighted training (inverse frequency) handles the 70/12/10/8 imbalance; evaluation reports per-class precision/recall/F1, not headline accuracy.

ModelWeighted PrecisionWeighted RecallWeighted F1
Logistic Regression (baseline)0.9980.9980.998
Random Forest (final)0.9990.9990.999

200 trees, maxDepth=10, class-weighted. Train 45,112 / test 14,888 rows, 75/25 split, seed=42.

Top feature importances

Engineered ratios rank alongside raw behavioral fields — the payoff of Phase 2.

Honest note: this is a Kaggle synthetic dataset, so 0.999 F1 is higher than we'd expect in production — feature importance is spread across ~15 features with no single leak, but a realistic target on live data is 80–90% F1. We treat this model as proof of the pipeline, not a performance guarantee. Full discussion in docs/fraud-classification-results.md.

Approach 2 — Clustering

K-Means finds 3 behavioral segments the fraud label can't see.

An independent, unsupervised lens: features deliberately exclude the fraud-flag columns used by the classifier, so clustering surfaces behavior/quality patterns a supervised label alone can't. k=3 selected by silhouette score over k=2..6.

Key insight

Cluster 1 has by far the lowest return rate but the highest quality-issue share — the two metrics move in opposite directions, which is exactly why a single blended "return rate" KPI hides this segment's problem from whoever owns it today.

This is a QA/vendor problem, not a fraud problem — cross-reference dominant product_category within Cluster 1 against return_reason to target the escalation.

What we're recommending

Three interventions, three owners — ship the free one first.

Ship this first, no ML required

Require photo evidence above a value threshold. The "high-value item + no photo evidence" pattern alone touches $1.88M of non-legitimate refund exposure across 4,673 orders — a policy rule, live immediately, independent of the classifier's rollout timeline.

01

Deploy the fraud classifier as a triage score, not an auto-block.

Route the highest fraud_signal_score decile + Cluster 0 to manual review; auto-approve the lowest-risk tail. Re-threshold asymmetrically — a false "Legitimate → Fraudulent Return" flag costs more in trust than a slow review costs in ops time.

Give Cluster 1's 38% quality-issue rate to QA, not fraud.

Cross-reference dominant product category × return reason within the core-legitimate segment to target vendor escalations — 73% of customers, near-zero fraud, but the highest quality complaint rate of any segment.

Tighten policy — don't investigate — for Cluster 2.
